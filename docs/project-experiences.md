# Conversation-driven project experiences

Chat is the shared entry point. Creating a blank project opens the same chat interface as New chat. A supported request can arrive as ordinary text, through a starter button, or later in an existing conversation. Prior messages do not disable experience detection.

## Current workflow

1. The preflight endpoint checks capability availability and existing media requirements. It does not call the old Ollama classifier. Text work enters the durable `project.experience.v1` run.
2. A fixed classifier candidate, GPT-6 Luna with low reasoning, returns a strict `ExperienceIntent`: action, supported project kind, target language, task complexity, whether interpretation is needed, and an optional clarification. It receives the full bounded user message, current project kind and tools, and recent conversation. The model cannot choose arbitrary provider names or execute a write.
3. A supported setup request attaches catalog components, saves the original brief and provisional starter plan, and returns the authored introduction for that experience. A standalone chat is associated with a new project only after this classification. Chat remains visible while the run completes. The UI then opens the matching editor or language tutor with a reduced-motion-aware arrival animation and staggered component tabs. A three-page tour appears once per account and experience type; completion is stored server-side. Missing language choices stay unset and are requested inline.
4. A brief that contains substantive context continues into a response stage. Follow-up messages take the same classifier and interpretation path. The response includes a natural reply plus structured changes to real editor fields, tasks, blueprint sections and Project Memory. Exact source quotations link every proposed change to the current message. Creative inventions must be authorized by the user's request and remain labeled as proposals.
5. Valid changes merge into the project. Disjoint edits can merge; a concurrently changed field, missing record, unknown field, or invalid source stops the update without overwriting current data. The paid reply and proposed changes remain saved for review. A durable pending marker recovers interrupted local writes without another provider call; workspace changes and their applied marker commit together. The chat links successful changes to their editors, and refresh preserves unsaved editor drafts.

Bare setup uses authored product copy. This is intentional onboarding, not a substituted model result. Detailed interpretation is a real model call and cannot be replaced with a template or repaired through repeated calls. The earlier `populate_after_chat` generic-template fallback is no longer used.

The intake classifier also returns a concise `project_title` for setup, using the subject and project type while preserving supplied names (for example, Apollo Lost Game or Learning Spanish). Only newly auto-created projects use this title; existing and manually named projects retain their names. Title generation shares the existing paid classification and checkpoint, with no extra request. Older checkpoints without a title use the language or catalog name. The October 8 classifier prompt remains a candidate: fixture tests cover persistence and name preservation, while semantic title quality still requires live evaluation and owner review using the qualification suite.

## Model floors and budget

The classifier is independent of the user's response selection. Basic starts with the current Sol low candidate, uses Sol high for standard creative development, and can promote to Astra high for complex work. Smarter cannot fall below Sol high; Super cannot fall below Astra high. Language tutoring is a separate fixed-baseline component: it does not expose or inherit the general-chat selector. It currently uses the Sol low candidate for new turns and explicit retries. General project-chat floors remain unchanged. No hosted-model outage falls back to Ollama.

Policies are versioned in `powwow/intelligence.py`. Intake and response stages record their models, settings, schemas, provider results and usage separately. They remain candidates pending live evaluation and owner review. Luna's current pricing and structured-output support were checked against [its official model page](https://developers.openai.com/api/docs/models/gpt-6-luna); schema handling follows [Structured Outputs](https://developers.openai.com/api/docs/guides/structured-outputs).

The server reserves a conservative bound for both stages before accepting a run. Completed classifier usage is charged immediately; remaining reservation is retained if response submission is uncertain. A stored classification is reused after a safe interruption. An uncertain paid submission is never repeated automatically. Completing a canned introduction releases the unused response reservation. Project input allowances now size the initial reservation only. Requests above that estimate use OpenAI's input-token count endpoint with the same input/schema, then atomically grow the reservation within the run and account spending budgets before generation. Project requests are not trimmed or rejected by Powwow's previous byte ceiling. Provider context capacity still applies; automatic whole-book chunking is not implemented.

## Project memory and isolation

Project Memory is a normal editable component. Character, manuscript, world and other editor records remain authoritative and are included in subsequent project interpretation, including across chats using project context. Private/chat-only and selected-context modes do not gain workspace access or mutation privileges. Authorized attachments, project instructions, grants and retrieved web sources retain their existing context boundaries. Each saved run keeps its source quotations and update provenance. `GET /v1/projects/{id}/memory.md` exports the project brief and records as Markdown after ownership checks. Connected local folders receive `project-memory.md` alongside `project.json` through the existing mirror.

Language tutoring continues to use its separate learner/day context and qualified-model policy. General project memory does not bypass learner isolation. Media generation retains its existing capability-specific routes; the new pipeline does not add unsupported image, video, or 3D tools.

## Qualification and verification

October 8 context packing: response requests include the current message once, outside recent conversation. Exact copies of a long current brief in project fields use lossless `$text_ref` / `$text_parts` transport references; persisted briefs and records remain unchanged. The subsequent revision removed the project byte ceiling and 30,000-character chat/brief caps; paid-request reservations remain enforced using exact provider counts for larger payloads. This fixes avoidable duplication, not unlimited document ingestion or model quality qualification. Regression fixtures exercise long book/game briefs, lossless reconstruction, sending large unique context intact, atomic reservation growth, budget rejection before generation, token-count failure and uncertain-submission retention. Live interpretation of the packed context still requires evaluation and owner review.

`evals/project-experience-quality.json` defines representative setup, paraphrase, ambiguity, negation, mixed-medium, rich-brief and follow-up cases. Run the live harness only with an ignored server-side `OPENAI_API_KEY` configured. Never put a key in browser variables, reports, screenshots or chat. `apps/api/scripts/project-experience-live.py` uses a temporary isolated database, real provider calls, a bounded account allowance, and stops on the first failed case. It never substitutes fixture results or repeats an uncertain submission.

API tests exercise protocol, billing, isolation, concurrency and persistence. Browser tests exercise navigation, introductions and visible editor updates. These do not establish semantic classifier accuracy, factual quality or natural teaching. The live gate remains pending until the configured provider is evaluated and the product owner reviews the experiences.

## Workspace presentation (October 7, 2026)

Each catalog kind defines its starter components, generally two to four. Language learning uses only the tutor. Novels start with Story & Plot, Timeline, Characters, and Book & Script Editor. Other components remain optional through Add components; task references no longer install additional components. Structured updates can still attach a relevant optional editor when the user's content needs it. Memory records persist without automatically adding another navigation tab.

Language and novel workspaces do not expose blueprint or task components. Legacy records are preserved; legacy novel blueprint text appears in Story & Plot as Story notes. Story & Plot supports premise, genre, themes and setting alongside plot beats. General project chat stays anchored beneath editors, while the tutor uses its own conversation composer in that position. The shared task board and planning refinement panel have distinct React keys to prevent duplicate reconciliation during refresh.

Language layout is centered and bounded, with mic and language setting next to Send. Phrase-bank UI and save buttons are disabled; saved phrase data remains intact. Browser dictation still uses a target/native language setting: omitting it does not provide reliable multilingual detection. Slow playback uses rate 0.6 and pauses between sentences, with a timeout for speech that never starts. Voice quality still needs a real device check; browser fixtures only establish control behavior.

October 7 verification: 157 relevant API tests passed (one environment-specific skip), including legacy note preservation, fixed tutor policy, tour ownership and idempotency. Browser fixtures passed 5 project handoff checks, 25 language/speech checks and 8 refinement/component checks; desktop and 320px/390px renders were inspected. Web production build passed. Generated Dart analysis has no errors and the existing upload null-comparison warning. These fixture runs made no paid model calls and do not qualify model or real microphone/voice quality.

Token-count integration follows [OpenAI token counting](https://developers.openai.com/api/docs/guides/token-counting). No live generation was performed for this revision; model qualification remains candidate. Provider context errors remain provider errors, not Powwow message-length limits.

## BREACHWATER output exhaustion regression (October 8)

The observed 28,522-character brief was accepted as 10,314 provider input tokens. The response then consumed all 4,096 allowed output tokens as reasoning and returned incomplete with no visible answer. This was not an input rejection or abuse classification. Project output targets are now 8,192 (low), 16,384 (high Sol), and 32,768 (Astra); reasoning floors remain unchanged. Every project response gets an exact input count, and the output allowance is fitted to the existing per-run budget after classifier cost. Admission reserves no more than that budget, and the worker checks the full stage cost atomically before submission. A high-reasoning route requires room for at least 8,192 output tokens rather than submitting a predictably starved request. Project generation permits a 600-second read timeout; uncertain submissions remain non-retryable automatically.

Incomplete responses retain their provider reason and report response_incomplete instead of the generic model_error. Completed failed-generation usage is still charged once. Text attachments are read fully from authorized stored files, rather than their 12,000-character previews. Explicit attachment evidence is available to classification and editor updates. Context assembly no longer drops whole selected sources at a 48,000-character threshold. Existing history windows, access scopes, file-size quotas and cost enforcement remain.

These changes do not add a native game engine/build runner or qualify the models for all tasks. Full API regression: 226 passed, 5 environment-specific skips. Live verification metadata is saved separately in evals/reports/breachwater-output-verification.json; one successful case is not a general quality approval.

Live BREACHWATER retry: input 10,385 tokens; output 17,385 tokens (3,106 reasoning); incomplete after 338.39 seconds; cost estimate $0.999988. This candidate failed full response completion under the existing $1 run budget. The subsequent intake prompt limits initial organization to 12 focused records, retains the full source brief, and defers complete implementation/code generation. That prompt revision is not yet live-qualified. Paid partial structured output is retained for review and never applied automatically. Do not claim this workflow has passed the owner quality gate.

The browser also had a hidden fixed $1 budget for all chat runs. Project submissions and explicit retries now use /v1/config.max_run_budget_usd (currently $5 locally); this is a maximum reservation, not a flat charge. Account spending limits still apply. Media/tutor budgets are unchanged. The live trial above used the previous $1 ceiling; the compact intake plus server-configured budget revision has not yet had a live generation trial.
